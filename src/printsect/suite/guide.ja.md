# printsect：プリントプローブでバグを見つける手順

C のバグを、ソースに出力の行（プローブ）を入れ、対象機器で動かし、どのプローブが何を出力したかを
読むことで絞り込みます。プローブの一覧の管理、ビルド、転送、コンソールの読み取り、ヒットの集計は
printsect が行います。どこを調べるか、結果が何を意味するかは、あなたが判断します。

`doctor` の結果がすべて ok でなければ、先にプロジェクトの設定をしてください（`guide` の
トピック `setup`）。

## ループ

1. **症状から始める。** 相手が何を見たのか、どうすれば再び起こせるのかを聞きます。何かを変える前に、
   その周辺のコードを読みます。知らないコードでは、`map` で部分ごとの構成と誰が誰を使うかを、`map_focus` で
   1 つの部分の入口を、`map_who` で 1 つの関数、変数、ファイルを誰が使っているかを見ます。
2. **仮説を一つ立てる。** たとえば「rx() が len 0 で呼ばれている」。1 つのプローブで 1 つの仮説を確かめます。
3. **プローブを入れる。** `probe_add` を使い、必ず `purpose`（何を確かめるためか）と `expect`
   （ヒットした場合・しなかった場合に何が分かるか）を書きます。仮説を決める値は `name=value` の形で
   出力します：`printf("[{tag}] len=%d state=%d\n", len, st);`。
   一度に入れるのは数個までです。分岐の入口に入れたプローブで、その分岐を通るかどうかが分かります。
4. **作り直す範囲を確かめる。** ヘッダや共通のファイルに入れるときは、`deps_which` で確かめます。
5. **実行する。** `run` を使い、結果の `hits` と `not_reached` を読みます。
   - ヒットしたプローブは値を出しています。仮説を確かめるか、捨てます。
   - 届かなかった（not reached）プローブも発見です。そのコードは実行されていません。
   - `banner_seen: false` は、出力が古いビルドのものかもしれないという意味です。信用しないでください。
   - `missed` の行があれば、出力の一部が読めていません。ヒット数は少なめに出ている可能性があります。
6. **分かったことを書き残す。** `probe_note` でプローブに書きます（例：「再接続後は毎回 len が 0」）。
   そのうえで範囲を絞ります。プローブを原因に近づけ、調べる範囲を毎回半分にして、もう一度実行します。
7. **原因が出力で示されたら止める。** 推測ではなく、出力で示されたときです。相手に、原因、根拠
   （プローブの番号、値、実行の番号）、考えられる修正を伝えます。
8. **後片付け。** `probe_clear` のあと、`probe_list` にあなたのプローブが一つも残っていないことを
   確かめます。

## 決まり

- プローブの行を自分で編集・削除しないでください。`probe_clear` は、エージェントが入れた行だけを
  正確に取り除き、ファイルを元どおりにします。`-AI` の付いていない目印の行は人が入れたものです。触らないでください。
- `run` のビルドが失敗したら、たいていはプローブのコードが原因です。そのグループを `probe_clear` で
  取り除き、`probe_add` で入れ直してから、もう一度実行します。
- **状態 `waiting_user`（終了コード 3）**：人が何かをする必要があります（自分の道具でビルドを
  読み込む、ケーブルを抜く、など）。メッセージのとおりに正確に伝え、終わったと言われるまで待ってから、
  `resume: true` を付けて `run` を呼びます。終わったと推測してはいけません。
- 対象機器をリセット、消去、書き換えするコマンドは、聞かずに送らないでください。
- 一度に入れておくプローブは少なくします（設定の上限でも止まります）。目的を果たしたプローブは取り除きます。
- `console_read` では、`since` に最後に見た `last` の番号を渡し、新しい行だけを読みます。
